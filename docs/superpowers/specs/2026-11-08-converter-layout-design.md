# 변환기 화면 배치 개선 — 설계

작성일: 2026-11-08 · 상태: 승인됨 (2026-11-08)

다음 프로젝트(별도 설계): 브라우저 안에서 엑셀 편집 — 이음오피스(pblsketch/ieumoffice)에서
영감. 이 문서 범위가 아니다.

## 왜

쓰는 사람의 말: "컨버터 기능 누르면 파일 다운 받는 위치가 동떨어진 하단에 표시되서
파일 수정상황을 쉽게 볼 수가 없다." PDF 편집기만이 아니라 **다른 변환기에서도 똑같이
불편하다**고 했다.

원인은 두 겹이다.

1. **페이지 틀.** `app/panel.ts` 는 머리말 → 도구 25개 버튼 격자(`.conv-choices`) →
   고른 도구(`.conv-stage`) 순으로 쌓는다. 도구를 누르면 제목에 `preventScroll`
   로 초점만 옮기므로, 도구가 첫 화면 밖 아래에 열리고 화면은 따라가지 않는다.
2. **도구 안.** 상태 줄(`.conv-status`)은 파일 칸 바로 밑에, 내려받기 링크
   (`.pdf-outputs`, `.conv-outputs` 등)는 설명·옵션을 한참 지난 아래에 따로 있다.
   PDF 편집기는 이 거리가 화면 한두 장이다. 쪽 목록도 글자("1. a.pdf · 원본 1쪽 ·
   90°")라서 회전·삭제·순서가 눈에 보이지 않는다.

## 목표

- **G1 페이지 틀 — 왼쪽 목록 + 오른쪽 도구 (쓰는 사람이 고름, 시안 B).**
  넓은 화면에서 도구 목록은 왼쪽에 늘 보이고, 고른 도구는 오른쪽 첫 화면 맨 위에
  열린다. 왼쪽에서 다른 도구를 누르면 바로 바뀐다.
  좁은 화면(휴대폰)에서는 목록이 "〈고른 도구 이름〉 · 다른 도구 고르기 ▾" 한 줄로
  접히고 도구가 그 바로 밑에 열린다.
- **G2 결과 칸 — 25개 도구 공통 (쓰는 사람이 고름).** 진행 상태·경고·내려받기
  링크를 **작업 칸 맨 위 한 곳**에 모은다. 상태 줄과 링크가 서로 떨어져 있지 않다.
- **G3 PDF 편집기 두 칸 (쓰는 사람이 고름, 시안 C).** 왼쪽에 쪽 썸네일 격자, 오른쪽
  맨 위에 결과 칸, 그 아래 저장·분할·"다른 형식으로"(HWPX·이미지). 회전하면 그림이
  돌고, 삭제하면 빠지고, 순서를 바꾸면 자리가 바뀐다. 좁은 화면에서는 위아래로
  쌓이고 결과 칸은 썸네일 바로 아래에 온다.

### 성공 기준

- 1366×768 데스크톱에서 아무 도구나 고르면 그 도구의 제목과 파일 칸이 스크롤 없이
  보인다.
- 같은 화면에서 PDF 편집기로 3쪽 PDF를 넣고 "전체 병합·저장"을 누르면 내려받기
  링크가 스크롤 없이 보인다. 다른 도구도 결과가 나오면 결과 칸이 화면 안에 있다
  (아래 "결과가 화면 밖일 때" 참고).
- 375×812 휴대폰 폭에서 도구를 고르면 도구 제목이 화면 안에 있고, 가로 스크롤이 없다.
- PDF 편집기에서 쪽을 회전·삭제·이동하면 썸네일이 즉시 그 상태를 보여 준다.

## 하지 않는 것

- **PDF 기능 추가.** 처음 요청의 "기능 강화"는 쓰는 사람이 **나중으로 미뤘다.**
  새 변환·편집 기능은 이 작업에 넣지 않는다.
- 끌어다 놓아 쪽 순서 바꾸기. 기존 "위로/아래로" 버튼으로 충분하다(내 판단).
- PDF 편집기 밖의 도구를 두 칸으로 바꾸는 일. 다른 도구는 한 칸 그대로이고 결과
  칸 자리만 옮긴다.
- 색·글꼴 등 전체 디자인 바꾸기.

## 이렇게 되면 실패다

- 결과가 두 군데(위 결과 칸 + 아래 옛 자리)에 나온다.
- 1,000쪽 PDF를 넣으면 썸네일 때문에 화면이 멈추거나 메모리가 터진다.
- 키보드·화면낭독기로 쪽 선택, 순서 바꾸기, 도구 고르기가 안 되거나 이름이 바뀐다.
- 도구를 오가면 넣어 둔 파일·설정이 사라진다(지금은 유지된다 — `panel.test.ts`).

## 지켜야 할 제약

- `AGENTS.md`: 기존 도구 ID, 접근성 이름, 변환 한도는 바꾸지 않는다. 파일은 브라우저
  안에서만 처리한다. UI는 `*-panel.ts`, 공통 UI는 `shared/kit.ts`(실제 공유일 때만).
- **도구 버튼의 접근성 이름.** 지금 버튼 글자는 제목과 한 줄 설명 두 `span` 이라
  이름이 "제목 + 설명"이다. 왼쪽 목록에서 설명을 화면에서 숨기더라도 DOM 에 남겨
  (시각적으로만 숨김) 이름이 그대로여야 한다.
- 브라우저 검사가 기대는 선택자는 유지한다: `.conv-choice[data-choice="…"]`,
  `aria-pressed`, `.conv-stage`, `.pdf-pages li`, `.pdf-pages input`(체크박스),
  `.pdf-outputs a`, 각 단추 이름("선택 쪽 ↻ 90°", "이미지로 저장" …),
  "N쪽 위로/아래로" `aria-label`. 바꿔야 한다면 `web/scripts/check-*.mjs` 와
  `app/panel.test.ts` 를 같은 변경에서 고친다.
- 렌더링은 이미 있는 PDF.js 경로(`features/pdf/pdf-render.ts` 의 `openPdf`,
  `renderToCanvas`)를 쓴다. 새 라이브러리는 들이지 않는다.
- PDF 한도(합계 64MB · 1,000쪽)는 그대로다.
- `prefers-reduced-motion` 이면 자동 스크롤에 애니메이션을 쓰지 않는다(지금 규칙과 같다).

## 정해진 것

### 페이지 틀 (`app/panel.ts`, `app/converters.css`)

- 넓은 화면: 두 칸 격자. 왼쪽 목록은 갈래(문서·PDF·이미지·텍스트·사무·파일)별 제목
  아래 도구 이름을 한 줄씩 세로로 늘어놓고, 화면에 붙어(sticky) 자체 스크롤한다.
  고른 도구는 `aria-pressed="true"` 와 강조색으로 표시한다(지금과 같은 속성).
- 왼쪽 목록이 자리를 차지하므로 본문 최대 폭 54rem 을 바깥 틀(`.shell`, 76rem)
  수준으로 넓힌다 — **내 판단.** 그래야 PDF 편집기 두 칸이 좁아지지 않는다.
- 왼쪽 목록에서는 한 줄 설명을 화면에서 숨기고(접근성 이름에는 남김), 마우스를
  올리면 `title` 로 보이게 한다 — **내 판단.**
- 아무 도구도 고르지 않은 처음 화면: 오른쪽에는 지금의 안내 문구(`placeholder()`)를
  둔다.
- 좁은 화면: 목록은 접힘 단추 하나("〈도구 이름〉 · 다른 도구 고르기 ▾",
  아무것도 안 골랐으면 "도구 고르기 ▾")가 되고 `aria-expanded` 로 열고 닫는다.
  처음 화면(아무것도 안 고름)에서는 펼친 상태로 시작한다. 도구를 고르면 접히고
  도구 제목이 화면 위에 오도록 스크롤한다.
- 도구는 지금처럼 처음 고를 때 한 번 만들고 들고 있는다(상태 유지).

### 결과 칸 (`shared/kit.ts` + 각 `*-panel.ts`)

- 결과 칸 = 상태 줄(`role="status"`, `aria-live="polite"`, 기존 `data-tone`
  규칙) + 경고 목록 + 내려받기 링크 묶음 + (있으면) 취소 단추. 한 상자 안에 둔다.
- 자리: **작업 칸 맨 위.** 한 칸짜리 도구에서는 파일 고르는 칸(또는 입력칸) 바로
  아래, 옵션과 실행 단추보다 위. PDF 편집기에서는 오른쪽 칸 맨 위.
- 한 도구 안에 독립된 작업이 둘 이상이면(ZIP 묶기/풀기, 시트 합치기/나누기,
  날짜·부가세 계산기의 각 칸) 작업마다 자기 결과 칸을 그 작업 칸 맨 위에 둔다.
- **화면에 직접 보이는 결과도 결과 칸에 함께 넣는다 (쓰는 사람이 고름).** 텍스트
  비교 표(`text-diff-panel`), QR 미리보기(`.qr-preview`), Markdown 미리보기
  (`hwpx-panel` 의 `pre.conv-preview`), 인코딩·가리기 미리보기, 이름 바꾸기·사업자번호·
  해시 결과 표가 여기에 든다. 상태 줄·내려받기 링크와 한 덩어리로 위에 나오고, 결과가
  나오면 입력칸·실행 단추는 그만큼 아래로 밀린다. 긴 표·미리보기는 지금처럼 자기
  상자 안에서 스크롤해(`max-height`) 입력칸을 끝없이 밀어내지 않게 한다 — 높이는
  만드는 사람 몫.
- 결과가 없을 때는 결과 칸이 자리를 차지하지 않는다(빈 상자를 보이지 않음).
- 계산기처럼 입력 즉시 값이 나오는 결과(`.conv-result`)는 이미 입력 바로 옆이므로
  자리를 바꾸지 않는다. 그 바로 위의 상태 줄(`date-panel`, `vat-panel` 위쪽 계산기의
  "날짜를 확인하세요" 등)도 그대로 둔다. `vat-panel` 에서는 품목 표 내려받기
  (`#vat-outputs`)만 결과 칸으로 옮긴다 — **내 판단.** 이 규칙은 "실행 → 상태 →
  내려받기" 흐름에 적용한다.
- 특정 입력칸·단추에 딸린 짧은 알림("복사했습니다", PDF 글자 고치기 편집 양식의
  "새 글자를 입력하세요." 같은 입력 확인)은 그 자리에 둔다. 결과 칸에 오는 것은 실행의
  진행 상태와 결과(성공·실패)다. 공통 부품도 이 둘을 구분할 수 있어야 한다 —
  **내 판단.**
- 공통 부품을 `shared/kit.ts` 에 하나 두고 25개 도구가 같이 쓴다. kit 을 아직 안
  쓰는 앞선 화면들(`pdf-panel.ts` 등)도 이 결과 칸으로 옮긴다. 기존 `outputs()`·
  `statusLine()` 은 이 부품 안으로 들어가거나 이 부품이 감싼다(이름·형태는 만드는
  사람 몫).
- **결과가 화면 밖일 때:** 결과(성공 링크 또는 오류)가 새로 나왔는데 결과 칸이
  화면에 보이지 않으면 결과 칸이 보이게 스크롤한다 — **내 판단.** 진행 중 상태
  ("PDF 읽는 중…")와 입력칸에 딸린 알림으로는 스크롤하지 않는다. 실행 결과(내려받기
  링크가 생김, 또는 실행 실패)일 때만 스크롤한다. 초점은 옮기지 않는다(상태 줄의
  `aria-live` 가 이미 알린다).

### PDF 편집기 (`features/pdf/pdf-panel.ts`)

- 두 칸: 왼쪽 = 파일 칸, 선택·회전·삭제·초기화 단추, 요약("N쪽 · M쪽 선택"), 쪽
  썸네일 격자(`ol.pdf-pages`). 오른쪽 = 결과 칸, 저장 단추(전체 병합·저장, 선택 쪽만
  저장), 분할 범위, "다른 형식으로" 아래 PDF → HWPX, PDF → 이미지.
- 썸네일 격자는 지금의 쪽 목록(`.pdf-pages` 의 `max-height` + `overflow: auto`)처럼
  **자기 상자 안에서 스크롤한다.** 그래서 1,000쪽이어도 위의 선택·회전·삭제 단추와
  오른쪽 칸(결과 칸·저장 단추)이 화면 밖으로 밀려나지 않는다. 상자 높이는 화면
  높이에 맞춘다(예: 첫 화면에 들어오도록). `IntersectionObserver` 의 root 는 이
  상자다 — **내 판단.** 좁은 화면에서도 격자는 자기 상자 안에서 스크롤한다.
- 썸네일 칸(`li`) 하나 = 쪽 그림 + 쪽 번호("1") + 원본 정보(파일명·원본 쪽, 작게)
  + 체크박스 + "N쪽 위로/아래로" 단추. 체크박스와 단추의 이름은 지금과 같다.
  그림을 누르면 체크박스가 바뀐다. 선택된 칸은 테두리로 표시한다.
- 회전: 쪽의 원래 회전은 렌더링에 반영하고, 편집기에서 더한 회전(`page.rotation`)은
  그림에 CSS 회전으로 즉시 보여 준다(다시 그리지 않음) — **내 판단.**
- 그리기 비용:
  - 파일마다 PDF.js 문서를 한 번 연다. 지금 `PdfSource` 는 pdf-lib 문서만 들고
    있으므로 원본 바이트(또는 연 PDF.js 문서)를 함께 들고 있어야 한다.
  - 화면에 들어온 칸만 그린다(`IntersectionObserver`). 동시에 그리는 수를 2장
    정도로 묶는다 — **내 판단.**
  - 썸네일은 긴 변 약 160px 기기 픽셀 수준으로 작게 그린다. 한 번 그린 그림은
    (파일, 원본 쪽) 단위로 들고 있어 순서를 바꿔도 다시 그리지 않는다.
  - "초기화"·파일 제거 시 PDF.js 문서를 `destroy()` 하고 그림을 버린다.
  - 그리다 실패한 쪽은 회색 칸에 "미리보기 없음"을 쓰고 편집·저장은 그대로 된다.
- 긴 설명문(HWPX·이미지 주의사항, 분할 문법 예시)은 `<details>` "자세히"로 접는다 —
  **내 판단.** 단추 이름과 한도 문구는 접지 않는다.
- 좁은 화면: 한 칸으로 쌓는다(왼쪽 칸 → 결과 칸 → 나머지). 썸네일 격자는 폭에
  맞춰 한 줄에 2~3개.

## 만드는 사람 몫

- 정확한 분기 폭(목록이 왼쪽에 서는 최소 화면 폭), 칸 폭, 간격, 색.
- 결과 칸 공통 부품의 이름과 API, 기존 `outputs()`·`statusLine()` 과의 관계.
- 썸네일을 `canvas` 로 둘지 `img`(Blob URL)로 둘지.
- 도구별 결과 칸 정확한 위치(위 규칙 안에서).
- 왼쪽 목록에서 키보드 이동을 화살표로도 할지(Tab 이동은 지금처럼 반드시 된다).

## 확인 방법

- `npm --prefix web test`, `npm --prefix web run typecheck`, `npm --prefix web run build`.
- `app/panel.test.ts`: 목록 배치가 바뀌어도 "한 번에 한 도구, 상태 유지, 실패 후
  다시 고르기" 검사가 통과하고, 좁은 화면 접힘 단추의 `aria-expanded` 를 검사한다.
- `web/scripts/check-converters.mjs` 와 `check-a11y.mjs`(실행 조건은 `VALIDATION.md`):
  기존 흐름 전부 통과. 추가로 1366×768 에서 도구 고르기 직후 파일 칸이, PDF 저장
  직후 `.pdf-outputs a` 가 뷰포트 안에 있는지, 375 폭에서 가로 스크롤이 없는지 본다.
- PDF 편집기: 회전 후 썸네일에 회전이 걸렸는지, 삭제·이동 후 칸 수와 순서가 맞는지,
  1,000쪽 PDF에서 첫 화면 썸네일이 뜨고 스크롤이 멈추지 않는지(수동 또는 검사).
